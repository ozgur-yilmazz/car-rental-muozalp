Suppose that you are working in a company as a software developer. Your company is developing a

responsible for developing all required Restful services which are required for web/mobile applications. 

Base Technical Requirements and Rules 

1. Create a Spring Boot web application. Use JPA and Spring Data JPA. You are not allowed to use pure 
JDBC and Spring JdbcTemplate. But you can use native SQL in the Data JPA Repositories. 
2. Generate an API documentation for your Restful services using OpenAPI (Swagger). Be careful, you 
will not develop a web application, you will use Swagger and it will produce the related API 
documentation. 
3. You are not allowed to use Entity Objects for the input and output of Restful services(in Controller 
layer). Your services should only accept and return Data Transfer Objects(DTO). You can use 
projection methods or a mapping library like mapstruct (https://mapstruct.org ) for such 
transformations. 
4. You are free to choose any database, but please avoid using any database-specific commands in 
your project. 
5. Switching to another database must be done easily by changing only application.properties file and 
the dependencies. 



6. You must initialize your database automatically with at least one record in each table. You are free to 
select any method you like for initialization. 
7. Draw a UML class diagram for your model classes. 
8. Develop seperate service classes for each entity. For example: ReservationService, CarService, 
MemberService etc. 
a. All service classes should contain all base methods for related Entity. For example your 
MemberService should contain methods for creating, reading a member and returning all 
members 
b. If you need, you can add extra methods for updating entity. 
c. You should also add any other required methods according to the business requirements(see 
below) 



9. Develop separate controller classes according to the RESTful Services requirements (listed below). 
For example: ReservationController, CarController, CarServiceController, MemberController etc 
10. Use a 3-layer architecture: Controller-Service-Repository. You can call Service beans from the 
Controller, and you can call Repository beans from the Service beans. However, you cannot call 
Repository classes directly from RestController classes 
11. Add Junit tests for testing all of your service methods 
12. Apply resource naming rules. 
13. It is forbidden to use FetchType.EAGER 
14. It is forbidden to use CascadeType.ALL and CascadeType.REMOVE. You can use the other cascade 
types depending on your requirements. 


RESTful Service Definitions 

Develop all necessary Restful services to satisfy all the UI service requirements listed below.

Service input/output parameters and business rules 

1 

Search available 
cars 

 

Input parameters: 

• category (optional) 
• transmission type (optional) 
• daily price range (optional) 
• pick-up date (required) 
• drop-off date (required) 
• number of seats (optional) 
• pickup location (required) 


 

Return Value : 

available car list. 

 

Business Rules: 

• Search for cars that match the entered criteria. Don't forget to check 
availability of cars: 
o Car statu must be "Available" (Check car’s statu) 
o Car must not be booked between the specified dates(Check all 
active reservations). 



• Be careful when creating your query: if a parameter is left blank, do not 
add it to your query 


 




Return Http Status Codes: 

• 200 => if available cars are found 
• 404 => if there is no available cars 


2 

Make a 
reservation 

Input parameters: 

• Car barcode number 
• Pick-up date and time 
• Drop-off date and time 
• Member id 
• Pick-up location code 
• Drop-off location code 
• Extra list 


Return Value : 

• Reservation number 
• Pick-up date-time 
• Drop-off date-time 
• Pick-up location code and name 
• Drop-off location code and name 
• Total amount 
• Member id 
• Member name 


 

Business Rules: 

Before making reservation you should check the car status again 

1. If status is not “Available” you can’t complete the reservation. You should 
send 406-Not Acceptable status code. In this case don’t create & save any 
Reservation object. 
2. If car status is Available you can complete reservation and send 200 Http 
status code. Following requirements must be provided: 
a. Generate a unique 8 digits reservation number in the Service layer. 
b. Set Reservation statu ACTIVE 
c. Assign reservation create date as sysdate 
d. Assign pick-up date and drop-off date 
e. Compute total amount : dayCount * car daily price + extra list 
prices 
f. Don’t save total amount into database, it must be calculated 
when requested 





Return Http Status Codes: 

• 200 – if the reservation is completed successfully 
• 206 – if selected car is not available

• Reservation number

boolean

• Return true if vehicle return is completed successfully. 
o Update reservation as follows:

▪ Return date = system date 



o If dropOffLocation of reservation is different from location of

• 200 – OK – if the car return is completed successfully

Main Objects And Properties 

The classes and properties listed below are only a rough draft. For the actual design, please carefully 
review the service requirements defined in this document. You may need to add new classes or 
properties 

Member 

All members can search the catalog, as well as reserve, pick-up, and return a car. 

Members can have 

• Name 
• Address 
• Email 
• Phone 
• Driving license number 


 

A member can reserve more than one cars 

Reservation 

Responsible for managing reservations for a car. 

Reservation may have 

• Reservation number (must be autogenerated 8 digit string) 
• Creation date 
• Pick-up date and time 
• Drop-off date and time 
• Pick-up location 
• Drop-off location 
• Return date 
• Statu 
• Member 
• Car 
• Extras 
• … 


Reservation can have different status: 

ACTIVE, COMPLETED, CANCELLED 

 

A car can be used for another reservation 




Location 

 

The car rental system has multiple locations, each location has attributes like 
code, ‘Name’ to distinguish it from any other locations. 

Each location has a code and a name. Such as: 

• 1-İstanbul Airport 
• 2-İstanbul Sabiha Gökçen Airport 
• 3-İstanbul Kadıköy 
• 4-İzmir City Center 


Car 

The basic building block of the system. Every car has a barcode, license plate 
number, number of seats, brand, model, mileage, transmission type, dailyPrice, 
category, location etc. 

 

Some of the categories are: 

• Compact car 
• Mid-size car 
• Large car 
• Station wagon 
• Luxury car 
• Minivans 
• SUVs 


Car status can be one of them: 

• AVAILABLE 
• BEING_SERVICED 


 

Transmission types: 

• Automatic 
• Manual 


Extra 
Service/Equipment 

Stores details about the various types of extras that members can add to their 
reservation. Some of them are: 

• Additional driver 
• Infant car seat 
• Car seat 
• GPS 
• Snow chains 
• Snow tires 
• Wifi router 


Each extra has a name and price. Price is not daily.
